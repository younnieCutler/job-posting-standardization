## 결정 1 — 어느 데이터로 클라우드에 올리나

**정한 것**: 합성(가짜) **일본어** 채용공고 트랙.

**대안**: 5차시 부하 테스트에 썼던 ATS(영어) 채용공고 트랙.

**왜**:
- 이 프로젝트의 핵심 가치는 "같은 공고가 사이트마다 다르게 표기된 걸 하나로 정리"다.
  그 지저분함(`Python` / `パイソン` / `PYTHON`)은 **일본어 데이터라야** 살아난다.
  ATS 영어 데이터는 표기가 깔끔해서 정규화할 게 없다.
- README 메인 아키텍처 그림이 원래 이 일본어 트랙이다. 6차시는 그 그림의 **꼬리를
  실제로 완성**하는 것.
- 5차시 부하·복구 실험 결과(영어 트랙, 25,684건)는 **그대로 인용**한다. 재실행 안 함
  (과제 지문이 허용).

**정리**: 5차시 = 영어 트랙으로 "많이 부어도 안 터진다" 증명 완료. 6차시 = 일본어
트랙으로 "끝까지(대시보드까지) 이어진다" 증명.

## 결정 2 — 데이터 창고: BigQuery (기결정, 6차시는 첫 구현)

**정한 것**: BigQuery (구글 클라우드의 SQL 데이터베이스).

**언제**: ADR-003에서 **2026-08-18에 이미 BigQuery로 확정**됨. 6차시는 새로 정하는 게
아니라 그 결정을 **처음으로 실제 구현**하는 것.

**대안**: Snowflake.

**왜 (ADR-003 요약)**:
- 결정 규칙 "데모용 시각화가 중요하면 BigQuery" — 이 프로젝트는 포트폴리오 대시보드가
  필요하므로 이 조건에 해당.
- BigQuery는 Looker Studio와 **무료 네이티브 연결**. 별도 BI 툴 비용 없음.
- `posting_id` 단일 컬럼 `MERGE`로 idempotency 구현하는 것도 BigQuery `MERGE` 문 기준으로
  이미 설계돼 있었음.
- 무료 크레딧(¥47,813) 안에서 이 규모는 사실상 0원.

> 주의: 설계 워크스페이스(`~/dev/career/job-data-foundry/`)의 ADR 사본은 구버전이라
> ADR-003이 아직 "미결정"으로 남아 있다. **정본은 제출 repo `docs/architecture_decision_record.md`.**

## 결정 3 — 대시보드 도구: 제출용은 Streamlit

**정한 것**: 이번 6차시 제출은 **Streamlit** (`app/dashboard.py`)로. 파이프라인이 저장한
**로컬 결과 파일을 직접 읽어** 리포트를 만든다. Looker Studio는 나중에 "정식 BI"로 얹을 수
있게 열어둔다.

**대안**: Looker Studio (지금 바로), Retool.

**왜**:
- Looker Studio는 브라우저 수작업이라 번거롭고 결과가 스크린샷뿐 → **재현이 안 된다**.
- Streamlit은 코드를 커밋하므로 **재현 가능 = 더 나은 제출 증빙**. `streamlit run` 한 줄.
- 과제 지문이 "Streamlit 데이터 연결"을 참고자료로 명시.
- BigQuery/dbt 마트는 아직 미구축 → Streamlit은 지금 로컬 parquet만 읽는다. 마트가 생기면
  그때 BigQuery 스냅샷 모드를 붙인다 (미구현을 완성 기능처럼 표시하지 않음).

**추가 결정 (2026-09-02) — 화면 원칙**:
- **두 데이터셋을 합치지 않는다.** 첫 화면에서 하나를 고른다:
  일본어 표준화 데이터셋(합성, 파이프라인 검증) / 글로벌 공개 ATS 데이터셋(실제, 시장 스냅샷).
  합산 KPI 금지 — 의미가 다른 데이터.
- 합성 데이터를 실제 일본 시장 수요·급여·경쟁률로 표현하지 않는다.
- 실제 ATS 데이터는 미국·글로벌 중심 → "일본 시장"이라 부르지 않는다.
- 개발자용 컬럼명·DB 용어를 화면에 노출하지 않는다. 차트 제목은 질문형. 섹션마다
  "보는 사람 / 답하려는 질문" 한 줄.
- 미구현(직무 분류, 연봉 파싱, 클라우드 저장/집계, 채용률·이탈률·경쟁률·실제 급여 벤치마크)은
  "아직 만들지 않은 것"으로만 표시.

**의미**: BI 도구는 ADR에 전용 항목이 없던 **진짜 미정 항목**이었다. 이번에 "제출용
Streamlit / 정식 후보 Looker"로 부분 확정. 완전 확정은 다음 라운드.

## 결정 4 — dbt 넣는다

**정한 것**: dbt Core로 표 3개 만들기 (원본 정제 1개 + 분석용 마트 2개) + 품질
테스트(`posting_id` 중복 없음 / 빈 값 없음).

**대안**: dbt 없이 BigQuery 뷰(SQL)만.

**왜**:
- 이 프로젝트가 증명하려는 축이 "데이터 표준화 + **데이터 거버넌스**"다. `dbt test`로
  품질을 자동 검증하는 게 거버넌스 축의 실물 증거다.
- 원래 설계(ADR-002)에 이미 확정돼 있던 것. 처음엔 마감 때문에 빼려다가 다시 넣기로.
- Airflow에서는 `BashOperator`로 `dbt run` + `dbt test` 호출 (설계 ADR-004 그대로,
  Cosmos는 다음 버전).

## 결정 5 — 재실행 안전성 방식이 바뀐다

**정한 것**:
- 로컬 = 지금처럼 **같은 날짜 폴더를 통째로 덮어쓰기** (재실행하면 그냥 새로 씀)
- 클라우드 = **`MERGE` (공고 ID 기준 병합)** — 이미 있는 ID는 갱신, 새 ID만 추가

**왜**:
- 5차시에서 발견한 것: "재실행해도 중복 안 쌓이는 이유는 파티션 덮어쓰기 덕분"
- 5차시에서 남긴 숙제: "BigQuery MERGE 단계로 가면 이 안전성이 **덮어쓰기 기반**에서
  **누적 기반(ID 병합)** 으로 바뀌어야 한다"
- 6차시가 바로 그 전환을 실제로 하는 것.

**확인 방법**: 같은 데이터를 두 번 적재해도 최종 건수가 안 늘어나면 성공.

## 결정 6 — 가짜 일본어 공고를 "진짜처럼" 만드는 방법 (4층 스택)

각 층이 다른 종류의 리얼리티를 담당한다.

| 층 | 뭐로 | 담당 | 이번에 함? |
|---|---|---|---|
| 1. 분포 | 후생노동성 **job tag** (일본판 직업사전, 500+ 직업의 실제 업무·연봉·경력요건, 무료·가공 허용) | 어느 직업이 실제 있고, 연봉대·경력요건이 시장과 맞나 | **O** |
| 2. 언어 | AI로 채용공고 문장 수천 개를 **미리 한 번만** 만들어 창고에 저장 → 이후엔 골라 끼우기 | 문장이 실제 공고 카피처럼 읽히나 | **X (다음)** |
| 3. 구조 | 공고 형식 골격 30~50개 손으로 작성 | 섹션 배치·사이트별 형식 차이 | **O** |
| 4. 지저분함 | 기존 골든셋 56행(실제 공고 표본) | `Python`/`パイソン` 같은 표기 흔들림, 등급 섞임 | **O (기존 유지)** |

**왜 2층은 다음으로**: AI 문장 창고 만들기는 하루 넘게 걸린다. 마감 안에 안 됨.
"파이프라인 안에서 AI 쓰지 않는다"는 원칙은 안 깨진다 — AI는 **재료 만들 때 한 번만**
쓰고, 파이프라인이 돌 때는 안 씀.

**핵심**: job tag 하나가 1층(분포)과 2층(AI가 만들 스킬 조합)을 **둘 다** 먹인다.

## 결정 7 — 데이터 건수는 나중에

**정한 것**: 이번엔 5,000~15,000건. 10만건 이상은 차차.

**왜**: 건수 늘리는 건 상수 한 줄 바꾸는 일. 본질은 리얼리티다. 리얼리티 뼈대(job tag +
템플릿)를 먼저 제대로 잡고, 볼륨은 나중에 채운다.

## 결정 8 — 로컬 실행은 그대로 둔다

**정한 것**: `docker compose up` / 로컬 파일 실행이 **여전히 기본**. 클라우드는
DAG 옵션(`push_to_cloud` 켤 때만) 으로 얹는다.

**왜**: 원래 설계(ADR-002)의 핵심 목표가 "노트북에서 완전 재현 가능"이다. 클라우드는
그 위에 얹는 추가 트랙이지 대체가 아니다. 마감 리스크도 준다 — 클라우드가 막혀도
로컬 경로로 제출 가능.
