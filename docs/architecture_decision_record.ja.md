## ADR-001: Spark vs DuckDB — 処理エンジンの選定

> **[2026-08-19 スコープ更新]** 初期設計にあった候補者/PII の処理範囲は、インタビュー後に削除されました。現在の JDF は日本 IT 求人票の標準化に限定するため、Spark 選定の根拠も現行パイプラインを基準に更新します。

### 1. 決定

**Apache Spark を Raw → Canonical の標準化区間の処理エンジンとして採用**します。
v1 は Local Spark で実行し、データ規模と運用要件が大きくなれば Dataproc や Serverless for Apache Spark のような Managed Spark 環境へ移行できるよう設計します。

### 2. 背景

JDF は7つの求人媒体（hrmos / doda / geekly / openwork / mid_tenshoku / talentio / company_site）の異なる Raw Schema を、ひとつの Canonical Schema に収束させる必要があります。

Spark の区間では、次のような Raw 中心の変換を担当します。

- 媒体ごとの Schema Mapping
- 日本語の文字正規化（NFKC など）
- 給与・日付・型のパース
- Taxonomy マッピング
- 重複除去と Canonical Schema の検証

目標データ規模は合成 Raw データで約1,000万件です。現在の規模なら単一マシンでも処理できる可能性はあります。それでも Spark を選ぶ理由は、単に「1,000万件だから」ではなく、**同じ変換コードをローカルで開発し、必要になった時点で分散処理環境へ拡張できる経路を確保するため**です。

BigQuery 以降の集計・Fact/Dimension・データマートのモデリングは dbt が担当します。つまり Spark と dbt の変換の役割を、Raw の標準化と分析モデリングに分離しています。

### 3. トレードオフ

| 項目 | **Spark（採用）** | DuckDB（不採用） |
|---|---|---|
| **拡張性** | 同じ API でローカル → 分散環境へ拡張できる | 単一マシンでの処理に最適化 |
| **大量データの変換** | パーティション単位の並列処理に強い | 単一マシン内の処理性能が優れる |
| **GCP 連携** | GCS / BigQuery コネクタを活用できる | 連携は可能だが主力の使い方ではない |
| **運用の複雑さ** | JVM・Spark 設定など管理要素が多い | 単一プロセスで単純 |
| **現在のデータ規模** | v1 ではやや過剰になり得る | 現在の規模だけ見ればより経済的 |
| **拡張の経路** | Dataproc / Serverless Spark へ移行できる | 規模拡大時に処理エンジンの再検討が必要 |

> **要点**: Spark は Raw データを Canonical Schema へ標準化する upstream の処理エンジン、dbt は BigQuery 投入後の分析モデリングを担当します。現在は Local Spark で再現性を確保し、実際の処理量が増えたら Managed Spark 環境へ拡張します。

## ADR-002: dbt Core vs dbt Cloud — 変換レイヤーの選定

### 1. 決定

**dbt Core（オープンソース）を採用**し、ローカルの Docker Compose 環境内で Airflow と直接連携します。

### 2. 背景

JDF の中心的な目標のひとつが、**完全にローカルで再現できるパイプラインのデモ**を組むことです。これが重要な理由は次の3つです。

- 読み手が `docker compose up` 一回でパイプライン全体を実行できる状態にしたい
- SaaS アカウントに依存せず、コード自体がポートフォリオの証拠になるようにしたい
- Public / Private の2ドメインがひとつのマートレイヤーに収束する構成で、マートの定義が頻繁に変わる。SQL だけで素早く反復し、`dbt test` で品質を自動検証したい

dbt Cloud は Managed Scheduler と IDE を提供しますが、その場合オーケストレーションのロジックが dbt Cloud の SaaS レイヤーに隠れてしまい、ローカル再現ができなくなります。

### 3. トレードオフ

| 項目 | **dbt Core（採用）** | dbt Cloud（不採用） |
|---|---|---|
| **ローカル再現性** | `docker compose up` で完全に再現できる | SaaS アカウント・API キーが必要 → 再現不可 |
| **Airflow 連携** | `BashOperator` で `dbt run` を直接呼ぶ（ADR-004 参照） | 独自 Scheduler を内蔵 → Airflow と役割が重複 |
| **運用の手軽さ** | プロファイル・環境変数を自分で管理する必要がある | UI ベースの管理で、初学者に優しい |
| **コスト** | 完全無料 | チームプラン以上は有料 |
| **説明のしやすさ** | 「オーケストレーション全体を自分で設計した」と言える | SaaS が代わりにやってくれたと受け取られ得る |
| **企業環境との近さ** | 大規模エンタープライズでは dbt Core + Airflow の組み合わせが一般的 | 中小規模チーム・スタートアップでの採用が中心 |

> **要点**: dbt Core を選んだ理由はコスト削減ではなく、**SQL だけでマートを素早く反復し、`dbt test` で品質を自動検証できる**からです。
>
> **[2026-07-26 更新]** 以前の版はこの決定の根拠を「Cosmos 連携のデモ」と書いていましたが、v7 のスコープ削減で Cosmos を外し `BashOperator` に確定しました。dbt Core の採用自体は有効ですが、根拠を差し替えています（詳細は ADR-004）。

## ADR-003: Snowflake vs BigQuery — DWH の選定

> **[2026-08-18 確定]** 下の §1 はもともと「未決定」として残していた版です。バッチ取り込みの構造を固めた時点で **BigQuery** に決めました。Looker Studio との無料ネイティブ連携（§3 の比較表のとおり）と、`posting_id`（`sha256(source_platform + source_posting_id)`）単一カラムの MERGE による冪等性の実装を、BigQuery の `MERGE` 文を前提に設計しています。§2〜§3 のトレードオフ比較はそのまま有効なので残します。

### 1. 決定

**BigQuery**。上の更新ノートを参照してください。

### 2. 背景

JDF パイプラインのサービングレイヤーとして使う DWH を選ぶ必要があります。両者はそれぞれ異なる強みを持ち、**日本の採用市場という文脈**でのポジショニングも考慮する必要があります。

- **Snowflake が有利な点**: 2024〜2026年の日本の IT 求人で Snowflake の言及頻度が増加傾向。特にデータエンジニアのポジションで「Snowflake 経験者歓迎」が多く見られます。
- **BigQuery が有利な点**: Google Looker Studio と無料でネイティブ連携でき、ポートフォリオのダッシュボードを別途 BI ツールの費用なしで可視化できます。

### 3. トレードオフ

| 項目 | Snowflake | BigQuery |
|---|---|---|
| **日本の求人キーワード** | ⭐ 歓迎条件として頻出 | 相対的に少ない（GCP スタックの企業に限られる） |
| **課金モデル** | コンピューティング（仮想ウェアハウス）+ ストレージの分離課金 | クエリ課金（少量なら無料枠を活用できる） |
| **BI 連携** | Tableau、PowerBI との連携に強い | Looker Studio と無料ネイティブ連携 ⭐ |
| **ローカル再現** | 不可（クラウド専用） | BigQuery Emulator（OSS）をローカルで使える |
| **dbt 互換性** | 完全互換、公式アダプタが成熟 | 完全互換、公式アダプタが成熟 |
| **学習コスト** | Snowflake SQL の方言がある | 標準的な BigQuery SQL（ANSI ベース） |

**判断の基準**:
- パイプライン完成後、**日本の求人票での Snowflake 言及率が40%以上**なら → Snowflake
- デモの可視化（Looker Studio の無料連携）の方が重要と判断されるなら → BigQuery

> **現状**: パイプラインのコア（Ingestion → Transformation → Serving）完成後、実際の求人票の分析を経て決定しました。どちらも dbt アダプタが完全にサポートされているため、乗り換えコストは低いままです。

## ADR-004: Airflow + BashOperator vs Cosmos — オーケストレーションの方式

> **[2026-07-26 更新 — 決定の反転]** この ADR の以前の版は Cosmos 採用として記録されていましたが、v7 のスコープ削減の見直しで決定が反転しました。以下は反転後の最終決定と、何がなぜ変わったかの記録です。

### 1. 決定

**`BashOperator` で `dbt run` を直接呼び出します。** Airflow + astronomer-cosmos の組み合わせは採用しません（v7 で v2 バックログへ延期）。

### 2. 背景

Airflow から dbt を実行する方法は大きく2つあります。

1. **BashOperator**: `bash_command="dbt run --select ..."` で dbt を subprocess として実行する。実装は単純だが、dbt 内部のモデル単位の成否が Airflow UI に出ない。
2. **Cosmos（astronomer-cosmos）**: dbt プロジェクトをパースして **dbt のモデル一つひとつを Airflow の Task に変換**し、モデル間の依存関係（lineage）を Airflow の TaskGroup として可視化する。

コードが0行の状態でスコープから点検し直した際、このプロジェクトの北極星（データ標準化 + データガバナンス）を基準に再判定した結果、Cosmos は **「Airflow UI で dbt のリネージがきれいに見える」という利便性の機能であって、標準化にもガバナンスにも当たらない**という結論になりました。依存関係をひとつ減らすことが完走リスクを下げる、という判断も働いています。

### 3. トレードオフ

| 項目 | **BashOperator（採用）** | Airflow + Cosmos（不採用） |
|---|---|---|
| **北極星との適合** | 標準化・ガバナンスのどちらにも必要条件ではない — Airflow の基本機能だけで、正規化→投入→マッチングの順序管理には十分 | dbt リネージの可視化は利便性の機能で、2軸のどちらにも掛からない |
| **導入の複雑さ** | Airflow の基本機能だけで実装できる ⭐ | `pip install astronomer-cosmos` の追加が必要 |
| **完走リスク** | 依存関係がひとつ少ない ⭐ | manifest.json のパースなど、新しく学ぶ面積が増える |
| **dbt リネージの可視化** | dbt 内部はブラックボックス、Airflow からは1 Task に見える | Airflow UI にモデル単位の Task として表示される |
| **Task 単位のリトライ** | dbt run 全体を再実行 | 失敗した dbt モデルだけを選んでリトライできる |
| **v2 での拡張余地** | Cosmos は v2 バックログとして保留 — 必要になればいつでも追加できる | — |

> **要点**: BashOperator を選んだのは「簡単な方に逃げた」からではなく、**このプロジェクトが示そうとしている2軸（標準化 / ガバナンス）のどちらにも Cosmos が必要条件ではない、という北極星の判定**によるものです。dbt のリネージが Airflow UI にきれいに出るのは良い機能ですが、このプロジェクトが証明すべきものではありません。v2 の拡張アイデアとして残します。

## ADR-005: Faker 合成データ vs 実際のスクレイピング — データソース戦略

### 1. 決定

**Python の `Faker` ライブラリ（ja_JP ロケール）による合成データ**をパイプラインの主データソースとして採用します。
実際の求人サイト（doda、Green、Wantedly など）のスクレイピングは行いません。

### 2. 背景

JDF は日本の IT 採用市場のデータを扱いますが、実サイトのスクレイピングには明確なリスクがあります。

- **利用規約違反**: doda、Green、Wantedly など主要な求人プラットフォームは、自動化されたデータ収集を明示的に禁止しています
- **法的リスク**: 不正競争防止法、個人情報保護法に抵触する可能性
- **公開のリスク**: スクレイピングで集めた実データを GitHub に公開すると、法的な問題になり得ます

一方、Faker による合成データには **意図的にノイズを注入できる**という独自の強みがあります。

- 実際の日本語データで起きる**表記ゆれのパターン**（全角/半角の混在、漢字・かな・英字の混在、給与表記の不一致など）を、意図してパイプラインに流し込める
- パイプラインの**正規化・クレンジングの能力**をデモできる
- 実際のスクレイピングよりも、むしろ**エンジニアリング能力の証明に向いた**データを作れる

### 3. トレードオフ

| 項目 | **Faker 合成データ（採用）** | 実際のスクレイピング（不採用） |
|---|---|---|
| **法的リスク** | なし ⭐ | 利用規約違反、法的責任の可能性 |
| **公開の可否** | GitHub 公開に問題なし ⭐ | 実データの公開 → 法的・倫理的な問題 |
| **ノイズ注入の制御** | 意図的にパターンを設計できる ⭐ | 実際に発生するノイズのパターンに従うだけ |
| **データの実在性** | 合成なので実市場の反映は限定的 | 実際の市場動向を反映する |
| **再現性** | シードを固定すれば同じデータセットを再生成できる | 収集タイミングによって変わる |
| **難易度のデモ** | 正規化ロジックの設計能力を示せる ⭐ | クレンジングより収集の能力が前に出る |

> **要点**: 合成データを選んだ理由は「実データが手に入らないから」ではなく、**利用規約に触れずにポートフォリオを公開しながら、同時にパイプラインの正規化能力を意図的に設計・デモできるから**です。「実データがなければ意味がないのでは」という問いへの先回りでもあります。
>
> **[2026-08-24 補足]** ただし現時点の生成データには限界があります。golden set（実データ）では職種名が94%、年収が59%のケースで媒体ごとに食い違うのに対し、生成データでは職種名と年収が全媒体で同一です。表記ゆれのうち最も難しい軸がまだ生成側に移せていません（[`data-spec.ja.md`](data-spec.ja.md) の「現時点の限界」を参照）。
